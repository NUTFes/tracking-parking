# 0003. カメラ入力での実機運用と事後分析用の録画

- ステータス: 採用
- 決定日: 2026-09-18
- 関連: [0002-api-event-delivery.md](0002-api-event-delivery.md)、ブランチ `feat/ucn/camera-input`

## 背景

ADR 0002 までの検証はすべて動画ファイル入力で行っていた。実機（Jetson Orin NX /
JetPack 6.x）へカメラを繋いだ段階で、動画ファイルでは現れない問題が続けて出た。
いずれも例外にならず、結果が静かにずれる種類のものだった。

1. カメラの解像度を設定していなかった。`cv2.VideoCapture` を開くだけで
   `CAP_PROP_FRAME_WIDTH/HEIGHT` を設定しておらず、envにも該当キーが無い。
   Logitech C270 は既定 640x480 で、1280x720 を出せるのに使われない。
   ライン座標は設定時の画角に紐づくため、実行時の解像度が違えば検知位置がずれる。
2. 時間窓の換算が公称fpsを前提にしていた。秒指定を開いた時点のfpsでフレーム数へ
   変換し、フレーム番号の差で判定していた。処理が撮影レートに追いつく前提であり、
   動画ファイルでは成り立つがライブカメラでは成り立たない。
3. フレームへ焼き込む日本語が `?` になっていた。`cv2.putText` の Hershey フォントは
   ASCII しか持たない。
4. 録画がカウント処理のフレーム予算を圧迫していた。`cv2.VideoWriter(mp4v)` の
   CPUエンコードは 1280x720 で約 11.6ms/フレーム掛かる。
5. 録画が単一の mp4 で、カメラ入力では出力名が固定だった。

## 決定

### 1. カメラの解像度をenvで明示し、ライン設定と同じ経路で要求する

`CAMERA_WIDTH` / `CAMERA_HEIGHT` / `CAMERA_FOURCC` を追加する。FOURCCを分けたのは、
解像度だけ指定しても通らない組み合わせがあるため（C270のYUYVは640x480までで、
1280x720はMJPGでしか出ない）。

要求は丸められうるので、設定後に必ず実測値を読み直し、一致しなければ警告する。
黙って進むと検知位置が静かにずれる。

`setup_lines.py` に `--camera` を追加し、解像度指定の実処理を
`common/camera.py`、envのパーサを `config.CameraCaptureSettings` へ切り出して、
検知ループとライン設定ツールが同じ値を通るようにした。**この一致を規約ではなく
コードで保つのが要点。** 別々に解像度を決めると、ライン座標の意味が両者で
食い違っても誰も気づけない。

### 2. 時間窓は「ストリーム時刻」の秒で判定する

入力の種類で時刻の作り方を変える（`compute_stream_time_sec`）。

| 入力 | ストリーム時刻 | 理由 |
|---|---|---|
| 動画ファイル | `frame_id / fps` | 全フレームを順に処理するので、処理時間に関係なく映像内の経過は変わらない。再現性が要る |
| カメラ | 処理開始からの実経過 | 処理が追いつかないとドライバのバッファ(4枚)で古いフレームが捨てられ、処理フレーム数は実経過より少ない |

実機の実測は公称30fpsに対し約14fps（推論60ms＋MJPGデコード11ms）だった。
`frame_id / fps` では「3秒」の窓が実時間で6秒以上に伸び、Line1とLine2の対応付けと
trackのクリーンアップの両方がずれる。

**動画ファイルでの挙動は変わらない。** 検証クリップのイベントログが変更前後で
完全一致することを確認した（`event_id` を除く10件すべて）。

この変更に伴い、`condition_key` の構成キーを `max_frame_gap` /
`cleanup_threshold`（フレーム数）から `max_frame_gap_sec` /
`cleanup_threshold_sec`（秒）へ入れ替えた。トラッカーの判定単位が秒になった以上、
フレーム数を条件として記録するのは実際の挙動と食い違う。**過去のW&B runとは
ハッシュが一致しなくなる。** 動画入力では `source_fps` を介して秒とフレーム数が
1対1に対応するため、情報量は落ちていない。

### 3. フレームへ焼き込む文字列はASCIIに限る

`cv2.putText` の Hershey フォントは ASCII しか持たず、非ASCIIは1文字ずつ `?` に
なる（`getTextSize("入口側")` が `getTextSize("???")` と完全一致することで確認した）。
この機体の OpenCV は `freetype` モジュールを含まないため、TTF描画へ逃げる手も無い。

Pillow と Noto CJK で描く選択肢もあったが採らなかった。ラベルは数語で、
フレームごとの ndarray↔PIL 変換のコストに見合わない。日本語で出したい説明は
フレームではなく端末側に置く（`setup_lines.py` は端末の案内を日本語のまま残し、
描画用のラベルだけ別に持つ）。

非ASCIIを足しても例外は出ず動画に `?` が並ぶだけなので、描画関数へ直接渡している
文字列リテラルをASTで集めてASCIIを確認するテストを入れた。

### 4. 各フレームへ日本時刻を焼き込む

事後分析では、動画のどの位置がいつなのかが分からないとイベント記録と
突き合わせられない。`frame_read_at`（APIへ送る `detected_at` と同じ値）を使う。
描画用に別途 `now()` を取ると動画とイベント記録がずれる。

タイムゾーンは固定オフセット+09:00へ変換する。`astimezone()`（機体の設定依存）
ではなく固定にしたのは、機体がUTC設定のままでも日本時刻を焼き込むため。
JSTは夏時間が無いので固定オフセットで厳密に表せる。

### 5. 録画はNVENCへ回す（OpenCVは再ビルドしない）

OpenCVのGStreamerサポートは無効（`cv2.getBuildInformation()` が `GStreamer: NO`）で、
`cv2.VideoWriter` からNVENCへは届かない。OpenCVを再ビルドする案は、
`.venv` がシステムのOpenCVを借りている構成（`--system-site-packages`）にも
影響するため採らなかった。

代わりに `gst-launch-1.0` を子プロセスとして起動し、生BGRフレームをstdinへ流す。
書き込みは 1280x720 で 11.6ms → **5.3ms** になった。

パイプラインの形は実測で選んだ。`nvvidconv` はBGRを受けられないため色変換が
必要だが、BGRx(4byte/px)を渡してハードウェア側で変換させる案はパイプへ流す
バイト数が増えるぶん遅かった（10.5ms）。CPUの `videoconvert` へ渡すほうが速い。

`queue` の `max-size-bytes` は明示的に0にする。既定10MBは生BGRの1280x720で
約3.8枚しか入らず、枚数指定が効かないまま間引かれていた（24枚投入して13枚）。

`leaky=downstream` を選んだのは、ディスク満杯などで下流が止まったときに
`stdin.write()` がブロックするとカウント処理ごと止まるため。**録画はカウントより
優先されない。** 実運用の間隔（80ms）では取りこぼしは起きないことを確認した
（60枚投入して60枚記録、検証クリップ1000フレームでも1000フレーム記録）。

### 6. 録画はサイズで分割する

mp4のインデックス(moov atom)は終了時に書かれるため、分割しないままプロセスが
落ちると**それまでの全録画が再生不能になる**。`SIGKILL` で落として実測したところ、
分割した4本のうち3本は再生でき、失ったのは書きかけの1本だけだった。

**時間ではなくサイズを基準にする。** `splitmuxsink` の `max-size-time` は
バッファのタイムスタンプ基準で、これは公称fpsから作られる。書き出しfpsが実効fpsと
一致しないため（下記「残っている既知の課題」）、「10分」の指定が実時間で約25分に
なる。バイト数はこのずれを受けない。正確な時刻は焼き込んだJSTから読む。

**保持数（`VIDEO_MAX_SEGMENTS`）を1以上にするとファイル名が循環する。**
`splitmuxsink` の `max-files` がリングバッファとして動くためで、2400フレームを
`max-files=3` で流すと index 0..2 の3本だけが残り、mtimeでは `segment_00000` が
最新だった。名前から時系列は読めない。cv2経路も同じ挙動へ揃えた（連番を増やして
古いものを消すほうが望ましいが、`splitmuxsink` をそう動かすには `format-location`
シグナル＝Python GIバインディングが必要で、この機体には無い。両者を食い違わせる
より本番で使う側へ揃える）。既定は0（無制限）で、事後分析用の証跡を黙って消さない。

カメラ入力の出力先は実行開始時刻のディレクトリにする。以前は
`annotated_camera.mp4` の固定名で、**起動するたびに前回の録画を上書きしていた。**
動画ファイル入力は従来どおり単一ファイルのまま（入力が有限で、名前が入力に
紐づくほうが扱いやすく、分割の動機も当てはまらない）。

## 残っている既知の課題

- **書き出しfpsが公称値のまま。** `cv2.VideoWriter` / `rawvideoparse` に渡すfpsは
  `CAP_PROP_FPS`（C270では30.0）で、実際に書かれるのは約12fpsのため、
  再生速度が約2.5倍になりファイルのdurationも実時間と合わない。各フレームに
  JSTを焼き込んだことで時刻からの位置特定はできるが、フレーム番号から時刻を
  計算するツールは誤る。実効fpsは起動時には分からないため、ウィンドウで測って
  から書き出す等の工夫が要る。
- **`"OUT"` → `"exit"` の変換が未検証。** 手元のクリップが入庫のみ（`out=0`）で、
  出庫を含むクリップが必要。宛先ではなく検知ループ側の話なので、本番へ送っても
  埋まらない。
- **検知ループからAPIへの配線がカメラ入力では未通過。** 開発機スタック相手に
  動画入力で10/10の突合を確認済みだが、カメラ入力で車両が写る条件をまだ作れて
  いない（検証環境に車が無い）。
