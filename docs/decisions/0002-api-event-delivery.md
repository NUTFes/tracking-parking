# 0002. 入出庫イベントをAPIへ送信する方式

- ステータス: 採用
- 決定日: 2026-09-15
- 関連: [0001-two-line-method.md](0001-two-line-method.md)「残っている既知の課題」、ブランチ `feat/ucn/api-event-delivery`

## 背景

ADR 0001 は「残っている既知の課題」として次の2点を挙げていた。

- Line2通過の扱いが未定。この信頼度（`high`/`normal`）をAPI送信や運用判断でどう扱うかを決める必要がある。
- 入出庫イベントをAPIへ送る処理が両方式とも未実装。方式共通の統合作業として残る。

受信側 [tracking-parking-api](https://github.com/NUTFes/tracking-parking-api) は既に
`POST /events` / `POST /heartbeat` / `POST /commands/{id}/ack` の3エンドポイントで
エッジ側からの入出庫登録・生存確認・コマンド結果報告を受け付ける設計で完成していた。
残る課題は、送信側（本リポジトリ）の実装と、それに伴う設計判断だった。

当初は「受信側APIを変更せずに成立させる範囲」と「べき等キーを追加する範囲」の2段階に
分けて計画していた。分けた理由は、受信側の変更に合意と実装の時間が読めないことだけ
だった。開発チーム内の相談の結果、受信側APIの担当者が決まりデプロイにも対応できる
ことが確認できたため、この理由が解消し、べき等キーを最初から入れた単一の実装として
進めることにした。

## 決定

### 1. confidenceを区別せず全件送る

`high`（Line2まで通過）と `normal`（Line1のみ）の両方を、区別せずそのままAPIへ送る。
受信側の `EventCreate` スキーマに confidence を受け取るフィールドが無いため、送るなら
区別なく載ることになる。一部だけ間引く案（`high` のみ送る）は、confidence の確定を
待つ必要が生じてイベントの送信が最大 `MAX_FRAME_GAP_SEC` 秒遅れる上、実装も複雑になる
ため採らなかった。検証データでは全128イベント中29件（約23%）が `normal` で、この分を
落とすと現場の実際の入出庫との差が広がる。

### 2. べき等キー（`request_id`）を最初から入れる

`POST /events` のリクエストに `request_id`（`EventLogger.record_event()` が返す
`event_id` のUUIDをそのまま使う）を含めて送る。受信側は `parking_events` テーブルへ
`request_id` のunique制約付きカラムを追加し、同じ `request_id` の2回目も**202
Accepted**で受理して既存イベントをそのまま返す契約とする。

この決定により、送信失敗の扱いが大きく単純になった。HTTPのタイムアウトは「リクエストが
サーバーに届かなかった」ことを意味しない。応答待ちで切れた場合、サーバーは既に
イベントを永続化済みかもしれない。べき等キーが無ければ、この「届いたか不明」な
失敗は安全に再送できず、二重計上を避けるために1件を諦めるほかなかった。`request_id`
があれば、届いていた場合はサーバー側で弾かれるため、届いたかどうかに関わらず再送して
よい。

**`POST /events` はイベントの永続化と `system_count` への反映を分離している。**
リクエストはイベントを永続化した時点で即座に **202 Accepted**（`status: "pending"`）
を返し、`system_count` への反映は `BackgroundTasks` によるキュー処理へ回る
（キュー処理間隔30秒・stale判定60秒）。したがって「同じ `request_id` を2回送って
`system_count` が1しか動かないこと」を確認するには、レスポンスを見た直後ではなく
`parking_events.status` が `processed` になるまで待つ必要がある。これは実装時点の
想定（同一トランザクション内で `system_count` を更新する）から変わった点で、
ローカル検証（`docs/decisions/`配下ではなく検証手順側に記載）で確認済み。

送信失敗は診断のため3種類に分類する（`src/tracking_parking/api/failures.py`）。

| 分類 | 意味 | 再送 |
|---|---|---|
| RETRY | リクエストが送られていないと確定（接続タイムアウト・接続拒否・名前解決失敗） | する |
| UNKNOWN | 届いたか不明（応答タイムアウト・送信後の切断・5xx・408・429・未知の例外） | する（`request_id`があるので安全） |
| DROP | 設定の誤り（408/429を除く4xx・URLの書き間違い） | しない |

RETRYとUNKNOWNは再送の可否としては同じ扱いだが、分類自体は診断のログに残す価値がある
ため維持している。1イベントにつき初回送信＋最大3回・指数バックオフ（1秒→2秒→4秒）で
再送し、それでも決着しなければローカルのJSONLスプールへ退避して、プロセス起動時に
全件（`request_id`があるので届いていたかを気にせず）送り直す。

### 3. 送信ガードは安全性の要件とする

カメラ入力であること **かつ** `API_ENABLED=true` であることの両方を満たすときだけ送信
する。動画ファイル入力では、`.env` の設定に関わらず常に送信しない。ファイル入力は
同じ動画をパラメータを変えて繰り返し処理する検証用途が前提で、送信が有効なままだと
検証の再実行のたびに同じ入出庫が本番の `system_count` へ積み上がってしまう。

この非対称性は意図的である。「ファイル入力でも**本番へ**強制送信する」逆向きの
オプションは提供しない。`--no-api` フラグ（`.env` を書き換えずに送信だけを止める、
実機デバッグ用）はカメラ入力側にのみ用意した。

**追記（2026-09-15）**: 上記とは別に `--simulate-camera-input` フラグを追加した。
カメラがまだ使えない段階（エッジ機の実機検証は動画→カメラの順で進める）で、
「実際の検知ループが検出したイベントが送信コードへ正しく届くか」という配線を
検証する手段が無かったため。単体テストはフェイク相手、`check_api_connection.py`
は検知ループを迂回するため、この配線だけが最後まで未検証だった。

このフラグは上記の禁止と矛盾しない。禁止しているのは「本番へ強制送信できる
手段を残すこと」であり、`--simulate-camera-input` は `API_BASE_URL` が
`is_local_network_url()`（`src/tracking_parking/api/settings.py`）でローカル/LAN
と判定できないときは `ApiRuntime.create()` が `ValueError` を送出して起動そのもの
をさせない。**逃げ道（override）は無い。** 本番/stagingへは構造的に到達できない
ため、規約ではなくコードでこの決定を保っている。`input_type` 自体は書き換えない
（`LINE_CONDITION_KEYS` のハッシュ元であり、`run_config` に嘘を記録しないため。
ガード判定にだけ `"camera"` として扱う）。

### 4. `restart` コマンドは未対応とする

デバイスへのコマンド（`restart` / `start_counting` / `stop_counting`）のうち、
`start_counting` / `stop_counting` は送信キューの有効/無効を切り替えるだけで実装できる。
一方 `restart` はプロセスそのものを再起動する必要があるが、本リポジトリにはプロセスを
起動・監視する仕組み（systemd unit、supervisor、docker restart policy 等）が無く、
`docker-compose.yml` もWeb側のサービスしか定義していない。

実装したふりをせず、`restart` を受け取ったら `failed` としてackし、
「プロセス管理の仕組みがないため手動で再起動してください」という理由を返す。将来
プロセス管理の仕組みを整備した時点で対応する。

補足として、`stop_counting` は送信だけを止める設計にしたため、`restart` で状態を
保持できない（起動直後は必ず送信する状態から始まる）ことと矛盾しない。仮に
`restart` を実装していた場合、「集計を止めたはずが再起動で勝手に再開する」という
運用上の落とし穴を生んでいた。

## 実装

- `src/tracking_parking/api/` — 送信機能一式（設定、失敗分類、HTTPクライアント、
  スプール、送信キュー、ハートビート、送信ガード）
- `scripts/run_detection.py` への組み込み — カメラ入力時のみ検出ループから送信キューへ
  積み、`finally` 節でflushする
- 詳細な設計上の判断は各モジュールのdocstringを参照

## 残っている課題

- 受信側APIへの `request_id` カラム追加・unique制約・重複時の応答契約は実装・
  マージ済み（`tracking-parking-api` の `parking_events.request_id`、unique index
  `ix_parking_events_request_id`）。べき等が実際に効くことは、ローカル開発スタック
  （`tracking-parking-center`）上で同じ `request_id` を2回送り、`parking_events.status`
  が `processed` になった後に `system_count` が1しか動かないことを確認済み。
- 受信側のDBスキーマ変更を伴うため、本番環境への反映は通常のデプロイ手順とは別に、
  インフラ担当との調整（マイグレーションの適用・ロールバック計画）が必要になる。
  ローカル検証はあくまで開発スタック上の確認であり、本番DBへの反映はこの限りではない。
